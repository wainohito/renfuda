- クラッシュ復旧のためのジャーナル(作らない)

## 2. 用語

| 用語 | 意味 |
|---|---|
| スタック | 1つのフォルダに入った、カードの集まり |
| テンプレート | 部品(フィールドなど)の配置と初期値の定義。HyperCardの「背景」にあたる |
| カード | テンプレートを1つ選び、フィールドの値を個別に持つもの |
| 部品(part) | テンプレート上の要素。値を持つもの(`text`、`number`、`bool`、`image`)と、持たないもの(`label`、`blank`、`button`、`counter`)がある |
| 孤立値 | カードに保存された値のうち、テンプレートの現在の定義に対応しないもの |

## 3. 拡張子とMIMEタイプ

| 種別 | 拡張子 | MIMEタイプ【案】 |
|---|---|---|
| マニフェスト | `.bdbm` | `application/x-vnd.bdb-manifest` |
| テンプレート | `.bdbt` | `application/x-vnd.bdb-template` |
| データ(カード) | `.bdbd` | `application/x-vnd.bdb-data` |
| テーマ | `.bdbs` | `application/x-vnd.bdb-theme` |
| スタックのフォルダ(目印) | `.bdbf` | なし(フォルダ名に付けるだけ) |

- 拡張子は小文字のみ。
- ファイルの種別判定には、拡張子に加えて、JSON先頭のキー(後述)を使う。
- MIMEタイプの `vnd.` 以降は仮の名前。公開前に決める。

## 4. ディレクトリ構成

```
MyStack.bdbf/
  <任意の名前>.bdbm           マニフェスト。ルートにちょうど1つ
  templates/
    <タイトル>-<id6>.bdbt
  cards/
    <タイトル>-<id6>.bdbd
  themes/
    <theme_id>.bdbs             このスタックで使うテーマのコピー
  media/
    image/<media_id>.<ext>
    audio/<media_id>.<ext>      予約(Phase 1 では使わない)
    video/<media_id>.<ext>      予約(Phase 1 では使わない)
```

- ルートに `.bdbm` が0個、または2個以上ある場合は、エラーにする。
- `.bdbm` をダブルクリックして開く場合、そのファイルの親フォルダがスタックのフォルダになる。
- `media/` の下は、メディアの種類ごとのサブフォルダ(`image/`、`audio/`、`video/`)に分ける。
- `themes/` には、このスタックのテンプレートが使うテーマのファイルを、コピーして置く(スタックを配布したときも、同じ見た目になるようにするため)。テーマの規則は、テーマ仕様。
- `cards/` の中は、サブフォルダを作らず、すべて `cards/` 直下に置く(新しいカードは直下に作る。既存のカードは、読み込んだ場所に保存し、移動しない)。ただし、読み込みでは、`cards/` の下をサブフォルダも含めて探す(深さ2まで)。件数が多いスタックで、将来フォルダを分けても読み込めるようにするため。
- 上記以外のファイルとフォルダは無視する。削除や変更はしない。
- シンボリックリンクは辿らない。無視する。

## 5. 共通ルール

### 5.1 エンコーディング

- JSONはUTF-8、BOMなし、改行はLF。インデントは2スペース。
- 構造に使う数値(座標、サイズ、`seq`、`rev`、`format_version`)は整数のみ。32bit版でも扱えるよう、`int32` を超える値を使うのは `seq` と `rev` だけ(64bit整数)。
- `number` 部品の値は、小数を含む有限のJSON数値。絶対値は 1e15 以下【案】。整数値は小数点なしで書く。小数は、読み直して同じ値になる最短の十進表記で書く。
- 文字列は保存された内容のまま扱う。Unicode正規化は行わない。

### 5.2 先頭キー(必須)

すべての `.bdbm`、`.bdbt`、`.bdbd` は、JSONオブジェクトの最初の2つのキーを次の順で出力する。

```json
{ "bdb": "manifest", "format_version": 1, ... }
```

- `bdb` の値は、`manifest`、`template`、`card`、`theme` のいずれか。
- MIMEの判定(sniffer)が、ファイル先頭の数十バイトでこの2つを見つけられるようにするため。
- 読み込み時は、キーの順序に依存しない。

### 5.3 ID

- 対象: `stack_id`、`template_id`、`card_id`、`media_id`
- 形式: 128ビットの乱数を、小文字のbase32(`a-z` と `2-7`、パディングなし)で表した26文字。正規表現は `^[a-z2-7]{26}$`。
- 乱数は、OSの安全な乱数源を使う。Haikuでは `arc4random_buf` か `/dev/random`(要確認)。
- IDは作成後に変更しない。

### 5.4 日時

- `created`、`modified` は任意。RFC 3339のUTC(例: `2026-10-14T12:34:56Z`)【案】。

### 5.5 未知のキーの保持(必須)

- 仕様にないキーや値は、読み込んだら捨てずに保持し、保存時にそのまま書き出す。
- 理由: 新しい版で追加された情報を、古い版が壊さないため。
- 未知の `kind` を持つ部品も、そのまま保持する。表示ではプレースホルダーにする。

### 5.6 上限(1か所の定数として定義する)【案】

| 対象 | 上限 |
|---|---|
| マニフェスト | 64 KiB |
| テンプレート | 256 KiB |
| カード | 4 MiB |
| JSONの入れ子の深さ | 32 |
| テンプレートの部品数 | 256 |
| 部品の表示名 | 64文字(コードポイント) |

- 読み込む前に `stat` でサイズを確認し、上限を超えるファイルは読まない(問題リストに記録する)。
- 同じオブジェクト内で、キーが重複しているJSONはエラーにする。

## 6. マニフェスト(`.bdbm`)

```json
{
  "bdb": "manifest",
  "format_version": 1,
  "stack_id": "abcdefghijklmnopqrstuvwxyz",
  "title": "朝の散歩",
  "created": "2026-10-14T12:00:00Z",
  "modified": "2026-10-14T12:00:00Z",
  "default_template": "<template_id>",
  "encryption": null
}
```

| キー | 型 | 必須 | 意味 |
|---|---|---|---|
| `stack_id` | ID | 必須 | スタックの識別子 |
| `title` | 文字列 | 必須 | スタックの名前 |
| `default_template` | ID | 任意 | 新規カードで最初に選ぶテンプレート |
| `encryption` | null | 必須 | Phase 1 では `null` 固定。`null` 以外なら「未対応のスタック」として開かない |
| `preset_description` | 文字列 | 任意 | プリセットの説明文。プリセットのマニフェストだけが持つ。新しいスタックには引き継がない |

## 7. テンプレート(`.bdbt`)

```json
{
  "bdb": "template",
  "format_version": 1,
  "template_id": "...",
  "title": "日記",
  "rev": 3,
  "size": { "w": 512, "h": 342 },
  "paper": { "size": "custom", "orientation": "landscape" },
  "theme": "beos",
  "background": { "color": "#f4f0e8", "image": null, "fit": "cover" },
  "title_part": "f_k3x9qa",
  "parts": [
    { "id": "f_k3x9qa", "name": "タイトル", "kind": "text", "rect": [16, 16, 480, 28], "default": "無題", "multiline": false },
    { "id": "f_m2w7ec", "name": "写真", "kind": "image", "rect": [16, 56, 200, 200], "default": null, "fit": "contain" },
    { "id": "f_p4ndhz", "name": "価格", "kind": "number", "rect": [224, 56, 120, 28], "default": null, "decimals": 0 },
    { "id": "f_t7ybqa", "name": "メモ", "kind": "text", "rect": [224, 96, 272, 160], "default": "", "multiline": true },
    { "id": "f_u5xkr3", "name": "", "kind": "blank", "rect": [16, 264, 200, 28] },
    { "id": "l_aa2b3c", "kind": "label", "rect": [16, 296, 200, 20], "text": "メモ" },
    { "id": "f_w3nzc6", "name": "読了", "kind": "bool", "rect": [352, 56, 100, 28], "default": false, "style": "switch" },
    { "id": "b_h4kq2d", "kind": "button", "rect": [224, 312, 60, 28], "text": "◀", "action": "card.prev" },
    { "id": "c_r7ymxa", "kind": "counter", "rect": [292, 314, 80, 24] },
    { "id": "b_v2pe5n", "kind": "button", "rect": [380, 312, 60, 28], "text": "▶", "action": "card.next" }
  ]
}
```

| キー | 型 | 意味 |
|---|---|---|
| `rev` | 整数 | テンプレートを保存するたびに増やす。1から始める |
| `size` | `{w,h}` | カード面の大きさ(ピクセル)。`w`、`h` は64〜8192【案】 |
| `title_part` | 部品のID | カードのタイトルとして使う部品。省略時は、最初の `text` 部品。それも無ければ「無題」 |
| `background` | オブジェクト | 任意。カード面の背景(第7章の「背景」) |
| `paper` | オブジェクト | 任意。用紙サイズと向き(第7章の「用紙サイズ」) |
| `theme` | 文字列 | 任意。使うテーマのID(テーマ仕様)。省略時は、既定のテーマ(`beos`) |
| `parts` | 配列 | 部品の一覧。上にある部品が下になる(描画順) |

部品の共通項目:

- `id`: `^[a-z][a-z0-9_]{0,31}$`。テンプレート内で一意。カードの `values` のキーになる。利用者には見せない。
  - 自動生成する。値を持つ部品と `blank` は `f_` + 6文字、`label` は `l_` + 6文字、`button` は `b_` + 6文字、`counter` は `c_` + 6文字。6文字は、OSの安全な乱数源から作った小文字のbase32(`a-z`、`2-7`)。
  - 連番にはしない。削除した部品のIDを新しい部品が再利用して、孤立値を引き継いでしまうのを防ぐため。
  - 作成後に変更しない。
- `name`: 利用者に見せる名前(日本語可、64文字以内)。値を持つ部品と `blank` が持つ。`label`、`button`、`counter` は持たない。名前を変えても `id` は変わらないので、カードの値には影響しない。テンプレート内で一意にすることを推奨する(読み込みでは、重複していてもエラーにしない)。
- `kind`: 部品の種類。
- `rect`: `[x, y, w, h]`。`int32` の整数。`w`、`h` は1以上。
- `style`(任意): 枠線、枠内の背景、文字の見た目。すべてのキーは任意。省略したキーは、テーマの値を使う(テーマ仕様の第5章)。
  - `border`: `{ "visible": true, "width": 1, "color": "#808080" }`。`width` は 0〜16 の整数(ピクセル)。
  - `fill`: 枠内の背景の色。`#rrggbb`。`null` は透明。
  - `font`: `{ "family": "...", "style": "Regular", "size": 12, "color": "#000000" }`。`family` と `style` は、Haikuのフォントの名前。`size` は 6〜96 の整数(ポイント)。指定したフォントがないときは、システムの標準のフォントを使う。
  - `font` は文字を表示する部品(値を持つ部品、`label`、`button`、`counter`)で使う。`border` と `fill` は、すべての種類の部品で使う。
- `locked`(任意): 真偽値。既定は `false`。`true` のとき、編集モードで、その部品の移動、大きさの変更、設定の変更、削除ができない(ロックの切り替えだけができる)。プレイモードでの値の入力やボタンの動作には、影響しない。
- `icon`(任意。`button` と `label` だけ): `{ "media": "<media_id>", "kind": "image", "ext": "hvif", "size": 24, "placement": "left" }`。メディア参照に、`size`(12〜128、既定は 24)と `placement`(`left`、`top`。既定は `left`)を加えたもの。`ext` は `hvif`(Haikuのベクターアイコン)、または画像の形式。文字列(`text`)と一緒に表示し、`text` が空ならアイコンだけを表示する。アイコンのファイルは、`media/image/` に置く(選んだアイコンを、スタックにコピーする。テーマ仕様の第6章)。
- `link`(任意。`image`、`label`、`button` だけ): クリックしたときに開くURL。`{ "url": "https://..." }`(固定のURL)、または `{ "field": "<部品のID>" }`(同じカードの `text` 部品の実効値をURLにする)。URLの規則(許可するスキームなど)は、入出力仕様の第2章。
- `source`(任意。`image` だけ): `{ "field": "<部品のID>", "max_edge": 256 }`。この画像が、同じカードの `text` 部品のURLから取得したサムネイルであることを表す。`max_edge` は、サムネイルの長辺のピクセル数(32〜2048)。CSV取り込みと、「画像を取得…」が使う(入出力仕様の第3章)。

実装する `kind`:

| kind | 値を持つか | 値の形 | 追加キー |
|---|---|---|---|
| `text` | 持つ | 文字列 | `multiline`(真偽値、既定は `false`)、`default`(文字列) |
| `image` | 持つ | `null` またはメディア参照 | `default`(`null` またはメディア参照)、`fit`(`contain`、`cover`、`stretch`) |
| `number` | 持つ | 数値または `null` | `default`(数値または `null`)、`decimals`(表示する小数の桁数。0〜6、既定は 0) |
| `label` | 持たない | なし | `text`(表示する文字列) |
| `blank` | 持たない | なし | なし。型を後から設定するための、未設定の枠 |
| `bool` | 持つ | `true`、`false`、`null` | `default`(`true`、`false`、`null`)、`style`(`switch`、`checkbox`。既定は `switch`) |
| `button` | 持たない | なし | `text`(ボタンの文字列)、`action`(動作。下記) |
| `counter` | 持たない | なし | なし。カードの位置(`12 / 300`)を表示する |

予約する `kind`(まだ実装しない): `date`、`audio`、`video`、`shape`

`blank`(未設定の枠):

- 枠だけを先に配置し、型を後から決められるようにするための種類。
- 値を持たない。カードの `values` には何も書かれない。
- 型を設定するときは、`kind` を `text`、`number`、`bool`、`image` のいずれかに変える。`id`、`name`、`rect` は変わらない。
- 型の変更の規則は、第20章。

### 用紙サイズ(`paper`)

テンプレートの `paper` は、用紙のサイズと向きを表す。省略できる。

```json
"paper": { "size": "A4", "orientation": "landscape" }
```

| `size` | 寸法(mm、縦向き) | カード面の大きさ(ピクセル、縦向き) |
|---|---|---|
| `A4` | 210×297 | 794×1123 |
| `A5` | 148×210 | 559×794 |
| `A6` | 105×148 | 397×559 |
| `B4` | 257×364 | 971×1376 |
| `B5` | 182×257 | 688×971 |
| `B6` | 128×182 | 484×688 |
| `postcard`(ハガキ) | 100×148 | 378×559 |
| `custom` | 任意 | テンプレートの `size` のとおり |

- B判は、JIS規格(B4 は 257×364 mm など)。ハガキは、通常のはがき(100×148 mm)【案】。往復はがきなどは、`custom` で扱う。
- `orientation` は、`portrait`(縦)または `landscape`(横)。横向きのときは、幅と高さを入れ替える。
- カード面の大きさの換算: ピクセル = 寸法(mm)× 96 ÷ 25.4(四捨五入)。カード面の座標は、96 dpi 相当の論理ピクセル。
- テンプレートの `size` が、常に正。`paper` は、PDF出力の用紙の大きさと、新規作成のときの選択の記録に使う。`paper` から換算した大きさと `size` が一致しないときは、`custom` として扱う。
- `paper` がないとき、または `custom` のとき、PDFのページの大きさは、カード面の大きさを 96 dpi で換算した値にする(例: 512×342 は、約 135.5×90.5 mm)。

### ボタン(`button`)

- 押すと、決まった動作をする部品。値は持たない。
- 追加のキー: `text`(ボタンに表示する文字列)、`action`(動作)。共通のキーとして、`icon`、`link`、`style`、`locked` も持てる。
- `action` は、次のいずれか。

| action | 動作 |
|---|---|
| `card.first`、`card.prev`、`card.next`、`card.last` | 最初・前・次・最後のカードへ移動する(検索中は、検索結果の中で移動する) |
| `card.new`、`card.duplicate`、`card.delete` | カードの追加、複製、削除(メニューと同じ。削除は確認する) |
| `list.open` | 一覧ウィンドウを開く |
| `link.open` | ボタンの `link` のURLを、ブラウザで開く |
| `find.start`、`find.run`、`find.clear` | 検索モードに入る、検索を実行する、検索を解除する(すべて表示) |

- `action` がない、または未知の値のボタンは、押しても何も起きない。未知の値は、そのまま保持する。
- `script` という `action` は、Phase 5(スクリプト)のために予約する。
- 動作するのは、プレイモードのときだけ(UI仕様の第6.10章)。

### 位置の表示(`counter`)

- カードの位置を `12 / 300` の形で表示する部品。値は持たない。
- 検索中は、検索結果の中での位置と件数を表示する。

### 背景(`background`)

テンプレートの `background` は、カード面の背景を表す。すべてのキーは任意。

```json
"background": { "color": "#f4f0e8", "image": { "media": "<media_id>", "kind": "image", "ext": "png" }, "fit": "cover" }
```

| キー | 内容 |
|---|---|
| `color` | 背景色。`#rrggbb`。省略したときは、システムのパネルの背景色 |
| `image` | 背景画像。メディア参照(`kind` は `image`)または `null`。省略したときは、画像なし |
| `fit` | `contain`、`cover`、`stretch`、`tile` のいずれか。既定は `cover` |

- 描画の順序は、背景色、背景画像、部品(`parts` の順)。
- 背景画像のファイルは、`media/image/` に置く(第9章)。
- 整理では、`background.image` の参照も、使用中のメディアとして数える(第13章)。
- 背景は、テンプレート単位。カードごとに変える機能は、まだない。

## 8. カード(`.bdbd`)

```json
{
  "bdb": "card",
  "format_version": 1,
  "card_id": "...",
  "template_id": "...",
  "seq": 2048,
  "rev": 7,
  "created": "2026-10-14T12:00:00Z",
  "modified": "2026-10-14T12:30:00Z",
  "values": {
    "f_k3x9qa": "朝の散歩",
    "f_m2w7ec": { "media": "<media_id>", "kind": "image", "ext": "png" },
    "f_p4ndhz": 1200
  }
}
```

### 8.1 実効値

テンプレートの値を持つ部品ごとに、表示する値を次の順で決める。

1. `values` にその部品の `id` のキーがあり、型が合っていれば、その値(`null` も有効)。
2. それ以外は、部品の `default`。

型の合致:

- `text` は文字列。
- `number` は有限の数値または `null`。
- `bool` は `true`、`false`、`null` のいずれか。
- `image` は `null` またはメディア参照(`kind` が `image` のもの)。

### 8.2 孤立値(必須)

次のどちらかの `values` のキーは、孤立値とする。

- テンプレートに、その `id` の値を持つ部品がない。
- 部品はあるが、値の型が合わない。

孤立値は、次のように扱う。

- 読み込み・保存のたびに、そのまま保持する。
- 表示では無視する。
- テンプレートを戻して型が合えば、自動的に復活する。
- 削除するのは、「スタック整理」(第13章)を実行したときだけ。

その他のカードの状態:

- `template_id` のテンプレートが存在しないカードも読み込む。値はすべて保持し、「テンプレート欠落」の印を付ける。表示は、キーと値の一覧にする。
- 未知の `kind` の部品に対応する値は、孤立値にしない(不透明な値として保持する)。
- 型を変えた部品に、新しい型で値を入力すると、同じキーの古い値は上書きされる。これは既知の制限(第20章、第22章)。UIで、上書きされる前に警告する。

### 8.3 `rev`

- 1から始め、保存に成功するたびに1増やす。
- Phase 3 で、BFS属性にも同じ値を書く。属性の `rev` と、ファイル本体の `rev` が違えば、属性を作り直す。

### 8.4 並び順(`seq`)

- `seq` は64bit整数。カードの並び順は、`seq` の昇順にする。同じ値のときは `card_id` の辞書順にする。
- 新しいカードを末尾に追加するときは、「最大の `seq` + 1024」にする。
- カードの間に挿入するときは、前後の `seq` の中間値にする。間が空いていなければ、周辺のカードに1024間隔で `seq` を振り直す(各カードを通常の保存手順で更新する)。

### 8.5 カードのタイトル

- そのカードのテンプレートの `title_part` に対応する値(第8.1章の実効値)の、1行目。
- 前後の空白を除く。空なら「無題」。
- ファイル名と、一覧の表示に使う。
- 値が数値のときは、第20.2章の `number` → `text` の規則で文字列にする。

### 8.6 仮カード(未保存の新規カード)

- 仮カード: `card_id` を持つが、まだファイルが作られていない新規カード。メモリ上だけにある。
- 仮カードは、利用者が値を、初期値(テンプレートの `default`)と違うものに変えた時点で、ファイルとして保存され、通常のカードになる(`rev` は1)。値を入力して、初期値に戻した場合は、変更なしとして扱う。
- 一度も変更されないまま、スタックを閉じたとき、別のカードへ移動したとき、アプリを終了したときは、ファイルを作らずに破棄する。破棄しても、ログには記録しない。
- 仮カードは、スタックのカード数には数えない。ただし、画面の位置の表示では、現在のカードとして数える(例: カードが0枚で、仮カードを開いているときは、`1 / 1`)。
- `seq` は、通常の新規カードと同じ規則(最後に追加するときは、最大の `seq` + 1024)で、保存する時点で決める。
- 保存したときに、`card.create` を記録する。
- `core` に、仮カードの作成と、変更があれば保存する操作(`commitIfChanged`)を用意する。

## 9. メディア

- 保存先: `media/<kind>/<media_id>.<ext>`。`<kind>` は `image`、`audio`、`video` のいずれか。Phase 1 で使うのは `image` だけで、`audio` と `video` は予約。
- 参照の形: `{ "media": "<media_id>", "kind": "image", "ext": "png" }`【案】。`kind` を参照に持たせるのは、部品が削除された孤立値の参照からでも、どのサブフォルダのファイルかが分かるようにするため。
- `ext` は `^[a-z0-9]{1,8}$`。画像の形式は、拡張子ではなく中身で判別する(Translation Kit)。
- パスは、検証済みの `kind`(上記の3つのいずれか)、`media_id`、`ext` からだけ作る。JSON内の任意の文字列をパスに使わない。
- メディアファイルは、保存時に一時ファイル経由で書く(第12章と同じ手順)。

## 10. ファイル名

通常のスタック(暗号化なし)のカードとテンプレート:

```
<整形したタイトル>-<id6>.<拡張子>
```

- `id6` は、`card_id`(テンプレートは `template_id`)の先頭6文字。
- 整形したタイトルは、次の手順で作る。
  1. `/ : * ? " < > | \` と制御文字(U+0000〜U+001F、U+007F)を `_` に置き換える。
  2. 先頭と末尾の空白(全角空白 U+3000 を含む)とドットを取り除く。
  3. 40文字(Unicodeのコードポイント)以内、かつUTF-8で120バイト以内に切り詰める。コードポイントの途中では切らない。切り詰めたあとに、末尾に空白やドットが残ったら、もう一度取り除く。
  4. 空になったら「無題」にする。
- 作成時に同名のファイルがあれば、新しいIDを振り直す。
- ファイル名は目印にすぎない。識別には、ファイル内の `card_id` を使う。
- タイトルが変わったときの改名は、ベストエフォート(第12章)。

暗号化スタック(Phase 4)では、`<id>.<拡張子>` のみにする(IDの全26文字)。タイトルを名前から推測できないようにするため。

## 11. 読み込みと検証

1. **入口**: `.bdbm` のパス、またはフォルダのパスを受け取る。
2. **マニフェスト**: 読み込んで検証する。`bdb` が `manifest` であること、`format_version` が整数であること、`stack_id` がID形式であること、`encryption` が `null` であること。
3. **形式バージョン**: `format_version` が実装の対応する版より新しい場合は、開かない(「新しい版のアプリが必要」)。古い場合は、メモリ上で最新の形式に変換する。変換のためだけに、ファイルを書き換えない。
4. **列挙**: `templates/*.bdbt` と、`cards/` の下の `*.bdbd`(サブフォルダを含めて、深さ2まで)を列挙する。次のファイルは無視する。
   - 拡張子が違うもの
   - 名前が `.` で始まるもの
   - 末尾が `.tmp` のもの
   - シンボリックリンク
5. **個々のファイル**: サイズ上限を確認して読み込み、検証する。壊れたファイルは、スタック全体の読み込みを止めずに、「問題リスト」に記録して飛ばす。
6. **IDの重複**: 同じ `card_id`(または `template_id`)を持つファイルが複数あるときは、`rev` が大きい方を採用する。同じなら、更新日時が新しい方を採用する。採用されなかったファイルは、削除せず、問題リストに記録する。
7. **インデックス**: メモリ上に `card_id` → `{パス, template_id, seq, rev, タイトル}` を作る。Phase 1 では、全ファイルを読んで作ってよい(Phase 3 で、BFS属性を使って高速化する)。
8. **何も実行しない**: スタックを開くだけで、スクリプトなどを実行しない。
9. **テーマ**: テンプレートの `theme` のテーマを探す(テーマ仕様の第3章)。見つからないときは、既定のテーマ(`beos`)を使い、問題リストに記録する(理由は `theme_missing`)。

## 12. 保存(アトミック保存)

カード、テンプレート、メディア、マニフェストは、すべて次の手順で保存する。

1. 内容をシリアライズする(`rev` を1増やし、`modified` を更新する)。
2. 保存先と同じディレクトリに、`<現在のファイル名>.tmp` を作って書き込む。
3. 書き込みに失敗したら、一時ファイルを削除して、エラーを返す。元のファイルは変更しない。
4. `fsync` する(推奨。BFSでの効果は要確認)。試作の計測(Linux VM)では、1回あたり約0.05秒。1枚ずつの操作では問題ないが、一括処理(整理、値の変換、`seq` の振り直し)では効くため、一括処理では、1枚ごとの `fsync` を省いて、最後にまとめて行ってよい【案】。
5. 一時ファイルを、現在のパスに `rename` で置き換える(原子的)。
6. タイトルが変わっていれば、現在のパスから新しいファイル名へ `rename` する。失敗しても、保存は成功として扱う。
7. 属性の更新(Phase 3)は、手順5が成功した後に行う。属性の更新に失敗しても、保存は成功として扱い、属性は古いものとして扱う。

競合の検出(最小限):

- 読み込み時に、ファイルの更新日時とサイズを記録しておく。
- 手順5の前に、保存先の更新日時とサイズを確認する。違っていたら、保存せずに「外部で変更された」というエラーを返す。呼び出し側が、上書きするか、読み直すかを決める。

## 13. スタック整理

孤立値の削除と、不要なファイルの掃除を行う操作。

1. **調査(dry run)**: 次を数えて返す。ファイルは変更しない。
   - 孤立値を持つカードの数と、孤立値のキーの数
   - どのカードからも参照されていないメディアファイルの数【案】。カードの `values`(孤立値の中の参照を含む)と、テンプレートの `default`、`background.image`、部品の `icon` を調べる。`themes/` のファイルは、削除しない。対象は `media/image/`、`media/audio/`、`media/video/` の下だけで、それ以外のファイルには触らない
   - `.tmp` ファイルの数
   - 読めないカードとテンプレートの数(0でなければ、実行してもメディアは削除されない)
2. **実行**: 呼び出し側が確認した後に呼ぶ。
   - 孤立値を持つカードを、通常の保存手順(第12章)で書き直す。
   - 不要なメディアファイルと `.tmp` ファイルを削除する。ただし、読めないカードやテンプレートがあるときは、メディアファイルを削除しない(読めないファイルが参照しているかもしれないため)。孤立値の削除と、`.tmp` ファイルの削除は行う。UIは、その旨を伝える。
3. この操作は元に戻せない。調査と実行は、別の呼び出しにする。

## 14. 安全性

- パスは、検証済みのID、`kind`、`ext`、列挙したファイル名からだけ作る。JSON内の文字列をそのままパスにしない(`..` や `/` を含む値で、スタックの外に出られないようにする)。
- シンボリックリンクは辿らない。
- ファイルは、`stat` でサイズ上限を確認してから読む。
- JSONの入れ子の深さ、部品数に上限を設ける(第5.6章)。
- 壊れたファイルや不正な値で、アプリが落ちてはならない。問題リストに記録して続行する。
- 利用者のデータを、自動で削除してはならない(削除は第13章の操作だけ)。
- ZIPを取り込む実装(将来)では、展開先の外へ出るパスの拒否、ファイル数と展開後の総サイズの上限、同名ファイルの検出を行う。

## 15. BFS属性キャッシュ(Phase 3 で実装。名前だけ予約)

カードのファイルに、次の属性を書く。属性は、ファイル本体から作り直せる派生データで、正本ではない。

| 属性名 | 型 | 内容 |
|---|---|---|
| `BDB:card_id` | 文字列 | `card_id` |
| `BDB:template_id` | 文字列 | `template_id` |
| `BDB:seq` | 64bit整数 | `seq` |
| `BDB:rev` | 64bit整数 | `rev` |
| `BDB:title` | 文字列 | カードのタイトル |
| `BDB:f:<part_id>` | `text` は文字列、`number` は倍精度小数、`bool` は真偽値 | その部品の実効値 |

- `number` を数値型の属性にするのは、BFSの数値インデックスで、数値としてのソートと範囲検索ができるようにするため。
- 属性が無くても、すべての機能が動くこと。
- **Phase 3 の目標**(試作の計測を受けて): 10万枚のスタックで、メモリ使用量を、試作(約257 MB、1枚あたり約2.6 KB)より大幅に減らす。BFS属性から、一覧と検索に必要な項目だけでインデックスを作り、カード本体は必要なときに読む【案】。32bit版でも動くことを条件にする。
- Phase 1 では書かないが、保存層に「保存が成功した後に呼ばれるフック」を用意しておく。

## 16. 暗号化(Phase 4 の予約)

- マニフェストの `encryption` が `null` 以外なら、Phase 1 では「未対応の暗号化スタック」として開かない。
- ファイルの先頭4バイトが `BDBE`(`0x42 0x44 0x42 0x45`)の場合は、暗号化コンテナとして予約する。Phase 1 では、「未対応の暗号化ファイル」として扱い、問題リストに記録する。
- 暗号化の詳細な形式(鍵スロット、チャンク構造、認証)は、別の仕様で定める。

## 17. コードの構成(要件)

- **`core`**: POSIXと標準C++だけに依存させる。BeAPIに依存させない。ID、ファイル名、JSONモデルと検証、実効値、保存層、アトミック保存、整理、ログを含む。Linux上でもビルドして、単体テストを実行できること。
- **BeAPI依存の部分**: UI、BFS属性、クエリ、ノードモニターは、`core` の外に置く(Phase 2 以降)。
- **保存層のインターフェース**: `core` に抽象インターフェース(スタックの保存層)を置く。Phase 1 の実装は、フォルダとJSONファイルによるもの。Phase 4 で、暗号化の層を差し込めるようにする。
  - マニフェストの読み書き
  - テンプレートの一覧、読み込み、書き込み
  - カードの一覧、読み込み、書き込み、削除
  - メディアの読み込みと書き込み(ストリームで扱う。メモリに全部載せない)
- **追加の操作**: プリセットから新規スタックを作る(第19章)、型の変更に伴う値の変換(第20章)、スタック整理(第13章)は、それぞれ `core` の関数として用意する。調査(dry run)と実行を分ける。
- **エラー**: 種別つきの結果型で返す。種別の例は、見つからない、形式が不正、上限超過、競合、書き込み失敗。例外の使い方は、実装側で決めてよい。
- **JSONライブラリ**: 実装側で選ぶ。要件は、未知のキーの保持、`bdb` と `format_version` を先頭に出力できること、重複キーの検出、32bit/64bitの両方で動くこと。試作では、`BJson` を使わずに自作した(キー順の保持、重複キーの検出、整数(`int64`)と小数の区別が必要なため)。

## 18. 受け入れテスト

Phase 1 は、次のテストが通れば完了とする。

1. **往復**: スタックを作成し、保存して、読み直した内容が元と一致する。
2. **未知のキー**: マニフェスト、テンプレート、カード、部品に未知のキーを足したファイルを、読み込んで保存しても、そのキーが残る。
3. **実効値**: `values` に値がない、`null`、型が違う、の3つの場合に、第8.1章のとおりになる。
4. **孤立値**: 部品を削除したテンプレートに対して、カードの値が残る。部品を戻すと復活する。整理を実行すると消える。
5. **整理の調査**: 調査(dry run)でファイルが変更されない。
6. **ファイル名**: 禁止文字、長いタイトル、空のタイトル、日本語のタイトル、先頭や末尾にドットや空白があるタイトルが、第10章のとおりに整形される。
7. **ID**: ID形式の検証。重複したIDを持つファイルを、`rev` の大きい方が採用される。
8. **アトミック保存**: 書き込みの途中で失敗させても、元のファイルが壊れず、一時ファイルが残らない。
9. **改名**: タイトルを変えて保存すると、ファイル名が変わる。改名に失敗しても、保存は成功する。
10. **競合**: 読み込み後に外部でファイルを書き換えると、保存がエラーになる。
11. **壊れたファイル**: 壊れたJSON、上限超過、キー重複のファイルが、問題リストに記録され、他のカードは読める。
12. **形式バージョン**: 新しい `format_version` を持つスタックは開かない。
13. **予約**: `encryption` が `null` 以外、先頭が `BDBE` のファイルは、「未対応」として扱われる。
14. **パス**: `..` や `/` を含むIDや `ext` を持つカードが、スタックの外のファイルにアクセスしない。
15. **規模(計測のみ)**: 10万枚のスタックで、読み込み時間と使用メモリを計測して報告する。`cards/` は平らなまま計測する。合否の基準は設けない。Trackerで `cards/` を開いたときの表示は、利用者が確認する。試作での参考値(Linux VM、`cards/` は平ら): 読み込み 2.7秒(2回目 1.7秒)、使用メモリ約257 MB、一覧の簡易検索 0.2秒、並べ替え 0.1秒未満、カード1枚の保存 0.05秒、整理の調査 0.4秒。
16. **数値**: `number` の値(`0`、`-1`、`0.1`、`1e-6`、`123456789012345`)が、往復で変わらない。上限を超える値は不正として扱われる。
17. **部品のID**: 自動生成したIDが形式に合い、既存のIDと衝突しない。
18. **未設定の枠**: `blank` の部品が、保存と読み込みで保持される。型を設定しても、`id`、`name`、`rect` は変わらず、カードの値には影響しない。
19. **型の変更**: 型を変えても、カードの値が消えない(孤立値として保持される)。元の型に戻すと復活する。
20. **値の変換**: 調査(dry run)で、変換できる件数とできない件数が返る。実行すると、変換できた値だけが書き換わり、できなかった値は保持される。
21. **プリセット**: プリセットから作ったスタックで、すべてのIDが新しくなり、カードと `default_template` の参照が追従する。元のプリセットは変更されない。
22. **空のスタック**: 空のテンプレートだけを持ち、カードが0枚のスタックが作られ、読み込める。
23. **メディア**: メディアが、参照の `kind` のサブフォルダに保存される。孤立値が参照しているメディアは、整理で削除されない。`media/` の下の未知のサブフォルダや、その中のファイルには、整理が触れない。
24. **再帰読み込み**: `cards/` の下のサブフォルダ(深さ2まで)に置いたカードも読み込まれ、保存したときは、その場所に書き戻される。新しいカードは、`cards/` 直下に作られる。
25. **ログの出力**: カードの作成・複製・削除・保存、テンプレートの保存、整理を行うと、それぞれ対応するイベントが1行ずつ記録される。各行が、単独でJSONとして読める。
26. **値を含めない**: カードの値、タイトル、表示名、検索条件の文字列を含む操作のあとで、ログのどの行にも、それらの文字列が含まれない(テストで検査する)。
27. **ログの失敗**: ログの保存先に書き込めない(権限がない、ディスクが一杯)ときでも、カードの保存などの操作が成功する。
28. **ローテーション**: 上限を超えると新しいファイルに切り替わり、保持期間を過ぎたファイルが削除される。
29. **並行**: 複数のスレッドから同時に記録しても、行が混ざらない。
30. **真偽値**: `bool` の値(`true`、`false`、`null`)が、往復で変わらない。`default` と `style` が保持される。
31. **ボタンと位置の表示**: `button`(`text`、`action`)と `counter` が、保存と読み込みで保持される。未知の `action` も、そのまま保持される。
32. **背景**: `background`(`color`、`image`、`fit`)が、保存と読み込みで保持される。`color` の形式(`#rrggbb`)が検証される。背景画像のメディアは、整理で削除されない。
33. **整理の安全策**: 読めないカードがあるときは、整理を実行しても、メディアファイルが削除されない。孤立値の削除は行われる。
34. **用紙**: `paper` が、保存と読み込みで保持される。7種類の用紙(A4、A5、A6、B4、B5、B6、`postcard`)の大きさが、第7章の表のとおりに換算される。向きを横にすると、幅と高さが入れ替わる。`size` と一致しない `paper` は、`custom` として扱われる。
35. **部品のスタイル**: `style`(`border`、`fill`、`font`)が、保存と読み込みで保持される。範囲外の値(`width` が 17、`size` が 5 など)は、不正として扱われる。
36. **ロック、アイコン、リンク、取得元**: `locked`、`icon`、`link`、`source` が、保存と読み込みで保持される。未知のキーも保持される。
37. **リンクの検査**: `http`、`https`、`mailto` 以外のスキーム、2048文字を超えるURL、存在しない部品や `text` 以外の部品を指す `field` は、無効として扱われる(入出力仕様の第2章)。
38. **仮カード**: 変更しないまま破棄したとき、ファイルが作られず、`card.create` も記録されない。値を変えて保存したとき、ファイルが作られ、`card.create` が記録される。入力して初期値に戻した場合は、保存されない。

## 19. プリセットと新規スタック

### 19.1 空のスタック(真っさらなカードから始める)

- テンプレート1つ: `title` は「無題」、`parts` は空。`size` と `paper` は、利用者が新規作成のときに選んだもの(UI仕様の第3.4章)。選ばなかったときは、`size` は 512×342、`paper` はなし。
- カード: 0枚。最初のカードは、初めてカードを入力するときに、仮カード(第8.6章)として開く。
- マニフェストの `default_template` は、そのテンプレートにする。
- 作成後、UIは編集モードで開く(Phase 2)。

### 19.2 プリセット(テンプレートから始める)

- 形式: 通常のスタックのフォルダと同じ。マニフェストと、`templates/` に1つ以上のテンプレートがあり、`cards/` は空。
- アプリに同梱する。読み取り専用で、直接は編集しない。
- 新規スタックの作成は、プリセットのコピーとして行う。コピー時に、次を行う。
  1. `stack_id`、すべての `template_id`、(カードがあれば)すべての `card_id` を、新しいIDに振り直す。
  2. カードの `template_id` と、マニフェストの `default_template` を、新しいIDに合わせて書き換える。
  3. 部品の `id` と `title_part` は変えない(テンプレート内で一意であれば足りる)。
  4. `rev` を1にし、`created` と `modified` を現在の時刻にする。
  5. ファイル名を、第10章の規則で付け直す。
- 同梱するプリセットの文言(`title`、部品の `name`、`label` と `button` の `text`)は、言語ごとに別のプリセットとして用意する(必須)。日本語と英語の2セット。UIの言語(UI仕様の第14章)に合わせて、`presets/ja/` か `presets/en/` を使う。英語のセットは、これから作る。
- プリセットの説明文は、マニフェストの `preset_description` に書く。新しいスタックには引き継がない。
- プリセットのテンプレートには、ナビゲーションの組(前のカードのボタン、位置の表示、次のカードのボタン)を含める(UI仕様の第6.10章)。

### 19.3 同梱するプリセットの内容【案】

日付型とチェックボックス型は後続のため、日付は `text` にする。

| プリセット | 部品(型) |
|---|---|
| 住所録 | 氏名(text、`title_part`)、ふりがな(text)、郵便番号(text)、住所(text、複数行)、電話(text)、メール(text)、誕生日(text)、メモ(text、複数行) |
| 書籍管理 | タイトル(text、`title_part`)、著者(text)、出版社(text)、ISBN(text)、価格(number)、ページ数(number)、購入日(text)、読書メモ(text、複数行)、表紙(image) |
| 名刺管理 | 氏名(text、`title_part`)、会社名(text)、部署・役職(text)、電話(text)、メール(text)、住所(text、複数行)、受け取った日(text)、メモ(text、複数行)、名刺の画像(image) |

- カード面は 512×342 を基本にする。配置(`rect`)は、Phase 1 では重ならない妥当な配置にし、Phase 2 のUIができてから調整する。

### 19.4 作成の手順

- 新規スタックは、同じフォルダ内の一時フォルダ(`.bdb-new-XXXXXX`)に作ってから、スタックの名前に改名する。途中で失敗しても、中途半端なスタックが残らないようにするため。
- 一時フォルダは、失敗したときに削除する。

## 20. 型の変更と値の変換

### 20.1 型の変更

- 部品の `kind` を、`blank`、`text`、`number`、`bool`、`image` の間で変える操作。`label`、`button`、`counter` との間では変えない。
- `id`、`name`、`rect` は変えない。種類ごとのキー(`default`、`multiline`、`decimals`、`fit`)は、新しい種類のものに置き換える。古い種類のキーは残さない。
- カードの `values` は、型を変えただけでは書き換えない。型が合わなくなった値は、孤立値として保持される(第8.2章)。型を戻せば復活する。

### 20.2 値の変換(任意の操作)

型を変えるときに、既存の値を新しい型へ変換する操作。型の変更とは別の関数として用意する。

- **調査(dry run)**: 全カードを調べ、変換できる件数と、できない件数を返す。ファイルは変更しない。
- **実行**: 変換できた値だけを書き換える。できなかった値は、そのまま保持される。各カードは、通常の保存手順(第12章)で書き直す。
- **変換の規則**:
  - `text` → `number`: 前後の空白を除いた文字列が、十進の数値として読めれば変換する(符号と小数点を許す。桁区切りのカンマと全角数字は変換しない)。空の文字列(空白のみを含む)は `null` にする。
  - `number` → `text`: 最短の十進表記(第5.1章)の文字列にする。`null` は空の文字列にする。
  - その他の組み合わせは変換しない(すべて「できない」として数える)。
  - すでに新しい型に合っている値は、「変換できる」「できない」のどちらにも数えない。
- この操作は元に戻せない。`text` と `number` を往復すると、表記が変わることがある(例: `"0123"` は `123` になる)。UIは、実行の前に確認する。

## 21. ログ

### 21.1 方針

- ログの実装は必須。ユーザーの動作と、エラーを記録する。
- ジャーナル(クラッシュ復旧のための書き込み前ログ)ではない。ログが無くても、スタックは完全に動く。ログの内容からデータを復元する機能は作らない。
- ログへの書き込みが失敗しても、利用者の操作は止めない(ベストエフォート)。失敗は、アプリの起動中に1回だけ通知する。

### 21.2 保存先

- スタックのフォルダの外に置く(アプリの設定フォルダの下)。スタックをZIPで配布したときに、ログが一緒に渡らないようにするため。暗号化スタックでも、ログがスタックの外にあることを前提にする。
- パス: `<アプリの設定フォルダ>/logs/<stack_id>/<YYYY-MM>.jsonl`【案】。設定フォルダの場所は、Haikuの標準の設定フォルダの下に、実装者が決める。
- スタックを開く前や、マニフェストが読めないなど、`stack_id` が分からないときは、`logs/_app/<YYYY-MM>.jsonl` に書く。

### 21.3 形式

- JSON Lines(1行に1イベント)。UTF-8、改行はLF。各行は、単独でJSONとして読める。
- 共通のキー:

| キー | 内容 |
|---|---|
| `t` | 時刻。UTC、ミリ秒まで(例: `2026-10-14T12:34:56.123Z`) |
| `level` | `error`、`warn`、`info`、`debug` のいずれか |
| `ev` | イベント名。`<対象>.<動作>` の形(例: `card.create`) |
| `stack` | `stack_id`(分かるとき) |

- イベントごとの追加キーは、第21.5章。読み手は、知らないキーを無視する。

例:

```json
{"t":"2026-10-14T12:34:56.123Z","level":"info","ev":"card.create","stack":"abcdefghijklmnopqrstuvwxyz","card":"...","template":"..."}
{"t":"2026-10-14T12:35:10.402Z","level":"error","ev":"card.save.failed","stack":"abcdefghijklmnopqrstuvwxyz","card":"...","err":"write_failed"}
```

### 21.4 レベル

| レベル | 内容 |
|---|---|
| `error` | 操作に失敗した |
| `warn` | 問題はあるが、続行できた(壊れたファイルを飛ばした、競合を検出した、など) |
| `info` | データやスタックの構造を変える操作、スタックやアプリの開閉 |
| `debug` | カードの移動、モードの切り替え、並べ替えなど、データを変えない操作 |

- 既定は `info` 以上。`debug` は、設定で有効にする。

### 21.5 記録するイベント

`core` が記録するもの(Phase 1):

| イベント | レベル | 追加キー |
|---|---|---|
| `stack.create` | info | `preset`(プリセットから作ったときの名前。空のスタックは `null`) |
| `stack.open` | info | `cards`、`templates`、`problems`(それぞれ件数) |
| `stack.problem` | warn | `reason`(壊れたJSON、上限超過、ID重複など)、`path`(スタック内の相対パス) |
| `card.create`、`card.duplicate` | info | `card`、`template` |
| `card.delete` | info | `card` |
| `card.save` | info | `card`、`rev` |
| `card.template_change` | info | `card`、`from`、`to`(テンプレートのID) |
| `card.save.failed` | error | `card`、`err` |
| `card.save.conflict` | warn | `card` |
| `template.create`、`template.save`、`template.delete` | info | `template`、`rev`(削除は不要) |
| `template.kind_change` | info | `template`、`part`、`from`、`to` |
| `template.convert` | info | `template`、`part`、`from`、`to`、`converted`、`skipped` |
| `media.add`、`media.replace`、`media.clear` | info | `card`、`part`、`kind`、`media`、`ext`、`bytes` |
| `stack.cleanup` | info | `orphan_cards`、`orphan_keys`、`media_deleted`、`tmp_deleted` |
| `stack.open.failed` | error | `err` |
| `stack.update` | info | `fields`(変更した項目。`title`、`default_template`) |
| `template.save.conflict` | warn | `template` |
| `template.save.failed` | error | `template`、`err` |
| `card.delete.failed` | error | `card`、`err` |
| `media.add.failed` | error | `card`、`part`、`err` |
| `theme.apply` | info | `template`、`theme` |
| `sample.copy` | info | `sample`(サンプルの識別名) |
| `link.open` | debug | `part`、`scheme` |
| `link.blocked` | warn | `part`、`reason`、`scheme` |
| `stack.csv_import` | info | `rows`、`cards`、`skipped`、`value_errors`、`images_ok`、`images_failed` |
| `image.fetch.failed` | warn | `card`、`part`、`reason` |
| `export.pdf` | info | `kind`(`card`、`cards`、`list`)、`count`、`pages`、`bytes` |
| `export.pdf.failed` | error | `kind`、`err` |

UI が記録するもの(Phase 2):

| イベント | レベル | 追加キー |
|---|---|---|
| `app.start`、`app.quit` | info | `version`、`lang`(UIの言語。`ja` か `en`) |
| `stack.close` | info | なし |
| `ui.search` | info | `conditions`(条件の数)、`results`(件数) |
| `ui.mode`、`ui.navigate`、`ui.sort` | debug | `mode`、`card`、`part` など |
| `ui.button` | debug | `part`、`action` |

- `err` は、種別を表す短い文字列(`not_found`、`invalid_format`、`limit_exceeded`、`conflict`、`write_failed` など)。メッセージの全文は書かない。

### 21.6 記録しないもの(必須)

- フィールドの値、カードのタイトル、テンプレートや部品の表示名、検索条件の文字列、パスワード、鍵、復号した内容。
- 理由: 住所録や名刺管理など、個人情報が入るため。ログは、不具合の報告などで、第三者に渡ることがある。
- 識別には、ID(`card_id` など)と、件数、種別だけを使う。
- 例外: `stack.problem` の `path`。問題のあったファイルを特定するために必要。ファイル名にタイトルが含まれうることを、実装者は知っておく。

### 21.7 ローテーションと保持【案】

- ファイル: スタックごとに、月ごと(`<YYYY-MM>.jsonl`)。
- 1ファイルが 10 MiB を超えたら、同じ月の次のファイル(`<YYYY-MM>-2.jsonl`、`-3` …)に切り替える。
- 保持期間は12か月。古いファイルは、アプリの起動時に削除する。1スタックあたりの合計が 100 MiB を超えたときも、古い順に削除する。

### 21.8 実装の要件

- `core` に、ログの出力先の抽象インターフェース(`LogSink`)と、既定の実装(ファイルへの出力)を置く。BeAPIに依存させない。
- テスト用に、メモリ上に溜める `LogSink` を用意し、差し替えられるようにする。
- 複数のウィンドウやスレッドから呼ばれる。スレッドセーフにする。1つのスタックにつき、ロガーは1つ。
- 1イベントは、1回の `write`(`O_APPEND`)で書き出す。バッファに溜めず、イベントごとにすぐ書く(クラッシュしても、直前までが残る)。`fsync` はしない。
- ホットパス(1キー入力ごと、スクロールごと)では、ログを出さない。

### 21.9 参照

- UIのメニュー「スタック」→「ログを開く」で、そのスタックのログのフォルダを、Trackerで開く(Phase 2)。アプリ内のログビューアは後続。
